`README.md` is the overview and setup for people, `docs/flows/` how each flow works end to end, and `docs/deploy.md` production. This file holds the conventions and the traps. A change to a flow updates its file in `docs/flows/`.

# Expo

When working in `app/`, read the SDK page for the module you are touching before writing code: `https://docs.expo.dev/versions/v58.0.0/sdk/<module>/`. The version index alone answers nothing. The API has changed, do not rely on what you remember.

# Generated types

`server/openapi.json`, `core/src/generated/api.d.ts` and `core/src/generated/limits.ts` are generated. Never edit them by hand. Change the Zod schemas in `server/src/<feature>/<feature>.dto.ts`, then from `server/` run `npm run types:gen`, and `npm run types:check` to verify sync. The generator writes them the way core's Prettier would, so formatting them changes nothing.

The server and the web client go live together; released apps lag behind for weeks (`docs/deploy.md`). Once the apps are in the stores, change the API by adding to it, and keep what a released app uses until it is gone.

`limits.ts` is the server's limits copied out for the clients: each one is set in the Zod schema next to its field (Better Auth's password rule in `server/src/auth/auth.ts`, how soon a mailed code may be asked for again in `server/src/auth/codeRequests.ts`), and the admin forms read the copy through the checks in `core/src/admin/drafts.ts`. To change a limit, change the schema and run `types:gen`.

`web/src/theme.css`, `web/src/components/icons/` and the theme-color meta tag in `web/index.html` are generated from `app/src/theme.ts` and the `ionicons` package. Every colour and radius live in `theme.ts`, each with a note on what wears it; a component never writes a colour of its own nor fades one with an opacity modifier, a new shade is a new name there. Change it or the glyphs and both clients follow. The generated files are committed; `npm run generate` in `web/` rewrites them, and `dev`, `build` and `check` run it first, so commit what it produces.

# Scripts

The root is an npm workspace of `core/`, `app/` and `web/` with one lockfile: run `npm install` there, never inside them. `server/` stays outside with its own.

Root

- `npm run check`: Prettier on the root's own files, `check` in every workspace, then `scripts/check-mirrors.mjs`.
- `npm test`: core's tests (Vitest), run in Europe/Stockholm and then America/New_York. The date helpers use local time, and only a negative offset catches a zone bug. Setting TZ inside a test does nothing.

`server/`

- `npm run dev`: Fastify on :3000 with watch, Swagger UI at /docs. The npm scripts set `NODE_ENV` (`development` for `dev`, the scripts and `types:gen`, `test` for `test`); anything else is production, where rate limiting is on, `/docs` and `/dev/codes` are gone, and `WEB_ORIGIN`, `SMTP_URL` and `MAIL_FROM` are required; `TRUSTED_PROXIES` lists the reverse proxies whose `x-forwarded-for` names the client. `org:create` and `admin:reset-2fa` default to development but keep a `NODE_ENV` already set, as the production container's. `BETTER_AUTH_SECRET` is required in every mode. `src/production.test.ts` is the only test that runs the server that way.
- `npm run check`: Prettier, TypeScript and the generated-types sync (regenerates and diffs, so it fails on uncommitted type changes).
- `npm test`: integration tests against brfhub_test on :5434. Needs `db:up`. It drops and re-pushes the test schema every run, since `drizzle-kit push` silently keeps the old schema there when it wants to prompt.
- `npm run db:up`: Postgres in Docker, dev on :5433 and test on :5434, and Mailpit, which catches every mail the dev server sends: read them at http://localhost:8025, or fetch the newest with `curl -s 'http://localhost:8025/api/v1/search?query=to:12@example.com' | jq -r '.messages[0].Snippet'`.
- `npm run db:seed`: resets bookings, subscriptions, resources, accounts, announcements and settings of the two seeded organizations; others, such as ones made with `org:create`, are left alone. Apartments sign in with the code mailed to them: Brf Exempel as `<number>@example.com`, Brf Andra as `<number>@andra.example.com`. Each admin signs in as `admin@` on the same domain with password `password` and then the authenticator code, and so does `styrelse@example.com`, who lives in apartment 31 of Brf Exempel and is both. In dev every mailed code is `123456` and the login and authenticator-setup screens fill in the address, the password and every code (from `GET /dev/codes?email=`; `npm run totp -- <email>` prints the authenticator's too), so signing in and setting up a new admin is taps alone. `DEV_SIGN_IN=off` in `server/.env` turns that off to test the real flow: the codes are random, read in Mailpit and from an authenticator app, and the screens leave them empty. Brf Andra keeps New York time and English alone, to see another time zone and a one-language organization with real data. The seeded apartments survive and any other moves out, but the accounts go with their sessions and push tokens, so sign in to the app again afterwards. It wipes bookings I may be testing with, so ask before running it.
- `npm run admin:reset-2fa -- <email>`: forgets an admin's authenticator and ends their sessions, for the last admin of an organization, whom no other admin can do it for.
- `npm run org:create -- --id <slug> --name <name> --time-zone <IANA zone> --admin-email <email> [--languages sv,en]`: creates an organization and its first admin, and prints the password once. The time zone cannot be changed afterwards; the languages, Swedish by default, can.
- `npm run push:test -- [organization] [apartment]`: releases an upcoming booking held by another apartment and sends the real notification to the watching apartment, `demo` and `12` by default. Reseed when it runs out of bookings.

`app/`

- `npm run android` / `npm run ios`: build, install and start Metro. Saving a file then reloads the app by itself. Rerun only after changes to `app.json` or a package with native code. `expo run` keeps an existing `android/` or `ios/`, so a change to `app.json` (icons, plugins) needs `npx expo prebuild --platform <android|ios>` first.
- `npm start`: start Metro alone, when the app is installed but Metro is not running.
- `npm run go`: Expo Go on a physical iPhone. UI only: push does not work there, and it throws on Android.
- `npm run check`: Prettier, TypeScript and ESLint.

Physical iPhone:

- `npx expo run:ios --device`, with Metro running. `ios/` is regenerated, so signing lives in `app.config.ts`, read from `app/.env`: `APPLE_TEAM_ID=<team id>` for a paid Apple Developer Program team, which signs push, or `APPLE_PERSONAL_TEAM=<team id>` for a free Apple ID, which strips the push entitlement a personal team cannot sign (the push token warning that follows is expected). After changing either, run `npx expo prebuild --platform ios --no-install` and then `pod install` in `ios/`: without `--no-install` prebuild asks to install packages, which a non-interactive shell cannot answer.
- Push to iOS also needs the APNs key in the Expo project, set with `npx eas-cli credentials -p ios` under Push Notifications, in the project named by `owner` and `extra.eas.projectId` in `app/app.json`.
- "No profiles found": Expo does not pass `-allowProvisioningUpdates`. Run `xcodebuild -workspace ios/BrfHub.xcworkspace -scheme BrfHub -destination id=<udid> -allowProvisioningUpdates build` once. A free team's profile expires after 7 days, then repeat.
- The phone must be unlocked, trust the developer under Settings, General, VPN & Device Management, and allow local network access.
- `expo run:ios --device` can hang at "Connecting to" the phone after the build succeeded. Install the built `Debug-iphoneos/BrfHub.app` from Xcode's DerivedData with `xcrun devicectl device install app --device <udid> <path>`, then `xcrun devicectl device process launch --device <udid> --payload-url <the bookslot:// URL below> com.bookslot.app`.
- "No script URL provided" means Metro is down or the app was opened without its URL: `bookslot://expo-development-client/?url=http%3A%2F%2F<mac ip>%3A8081`.
- After an Xcode update `xcrun` fails with code 69 until the user runs `sudo xcodebuild -license accept && sudo xcodebuild -runFirstLaunch`. A codesign keychain password prompt the user cannot answer means a certificate Xcode did not create: delete it in Keychain Access and let `-allowProvisioningUpdates` create a new one.

`web/`

- `npm run dev`: Vite on :5173. Reads the API from `VITE_API_URL`, default http://localhost:3000.
- `npm run build`: typecheck and production build into `dist/`. The routes are real paths, so whatever serves `dist/` has to rewrite unknown paths to `index.html`. `dev` and `preview` already do, which is why a missing rewrite only shows up once it is deployed.
- `npm run generate`: rewrites the generated theme and icons, see Generated types. Runs by itself before `dev`, `build` and `check`.
- `npm run check`: Prettier, TypeScript and ESLint.

Agents may start, restart and stop the `server/` and `web/` dev servers. One may already be running: check with `lsof -tiTCP:<port> -sTCP:LISTEN` and reuse it. Vite HMR and `tsx watch` pick up changes without a restart.

# Clients

- The server owns the booking rules, all in `server/src/booking/lifecycle.ts` (book, queue, release, an apartment letting everything go, the admin cancelling what a change leaves without a slot), under the apartment's lock. Push to a queue goes out after the response through the notifier `buildApp` is given; tests pass `memoryPush()` from `server/src/test/fixtures.ts` and await `server.notifier.idle()` before looking at what was sent, or `checkReceiptsNow()` for what Expo's receipts report later.
- Bookings are promised, free slots are not: the booking window only says how far ahead apartments book. An admin's new times, removed change or closing may start before a resource's `freeFrom` only after the client has shown the bookings it cancels (`POST /admin/resources/:id/preview`) and sends their ids back; the server refuses one it was not shown, and the apartments are told by push and mail. A closed resource stays visible to residents with the admin's note until it is removed.
- The client renders what it is told. What a time or a queue place offers (label, look, whether it can be pressed, what pressing does) is decided in `core/src/booking/offer.ts`; the clients only map it to their classes.
- An account (`user`) belongs to one organization and is a resident (`memberId`), an admin (`admin`) or both; `getSignedIn` in `server/src/lib/user.ts` answers with both parts. Both roles land on one account from either side: adding an admin with a resident's address, or an apartment with an admin's, in the same organization. Residents sign in with a code mailed to them (Better Auth's `emailOTP`), admins with a password and then a code from an authenticator app (Better Auth's `twoFactor`, with backup codes and a trusted device). Two clocks: an admin's session ends 7 days after sign-in, and a device trusted at sign-in then signs in again with the password alone for 30 days, renewed at each such sign-in. Signing out, a new password (reset with a mailed code or changed inside the app) or another admin's reset forgets the trusted device, an admin cannot turn their authenticator off, read its secret out or make new backup codes themselves, and no account sets its own name through Better Auth's `update-user` (the admin's forms do, with the text checked); the hooks in `server/src/auth/auth.ts` hold these on Better Auth's own routes, and the admin's week there too; `POST /sign-in/method` tells the login screen which, and sends an admin without a password straight to choosing one. An admin sets or resets the password with a mailed code, which ends their every session and trusted device; a resident made admin is signed out everywhere and chooses one the same way at the next sign-in. `getAdmin` refuses everything but the account until the authenticator is set up, which `AccountGate` shows as `TwoFactorSetup`. `AccountGate` in `src/auth/account.tsx` picks the app from the account and a mode, held as state in the app and read from the route on web; an account with both switches through `SwitchModeContext`. The admin app mounts no booking screens or push.
- A step down in an admin tab (a thing, a form on it) is an `AdminLocation` in `core/src/admin/location.ts`, with its address and the step above. Pages read it through each client's `useAdminLocation`: the web keeps it in the address, so back, forward and reload work, and the app in state, where it also answers Android's back button. A new admin page adds its step there, never local state.
- Every admin write logs an event from its route through `logEvent` in `server/src/event/event.service.ts`, shown under Föreningen / Association; a new admin route logs one too, with a subject the admin would recognise.
- Admins of an organization are equals who trust each other: nothing guards one admin against another beyond the event log, admin addresses are not secrets, and one address belongs to one organization. Do not propose role levels, approval steps or hiding admins.
- Push has a channel per kind (`slots`, `announcements`), which Android lists so each can be muted. A new or edited announcement is pushed to every apartment through `announceToApartments`. The apartment's switch under Lägenhet / Apartment keeps its wish in `lib/pushPreference.ts` on the device; off drops the token, and a device the OS has been told no on can only be turned back on in its settings.
- `app/` keeps the keyboard off the focused field with `react-native-keyboard-controller` (`KeyboardProvider` in `App.tsx`, `KeyboardAwareScrollView` and `KeyboardToolbar` in `AdminPage`), not React Native's `KeyboardAvoidingView`, which cannot shrink the window under Android's edge-to-edge. It is a native module: rebuild with `npm run android` or `npm run ios`.
- Mail goes through `server/src/lib/mail.ts` (SMTP, Mailpit in dev) the way push goes through `lib/push.ts`; the texts live in `server/src/mail/mail.service.ts`, and tests read what was sent from `memoryMail()` in `server/src/test/fixtures.ts`.
- Both clients draw the phone tab bar themselves in `src/components/TabBar.tsx`, a glass pill floating over the page (Liquid Glass on iOS 26 through `expo-glass-effect`). A page scrolling under it pads its end to clear it: `usePageEnd()` in the app, `--tab-bar-clearance` on the web.
- `web/` is one app. Below 1024px it renders the same screens as `app/`; above it renders the calendar and day view in `src/desktop/`, which loads the whole booking window for every resource in one `/schedule` request.
- `core/` (`@brfhub/core`) holds what both clients share: the API types and the client's core (`createApi`), error codes, i18n, date helpers, the load state (`load/`), and the actions behind the member and admin screens (`booking/bookingActions.ts`, `admin/actions.ts`), which ask through the `Dialog` port, and the steps of signing in, setting up the authenticator and changing the password (`auth/signIn.ts`, `auth/twoFactorSetup.ts`, `auth/changePassword.ts`), which reach Better Auth through the `AuthClient` port and tell its refusals in `auth/failures.ts`. It is TypeScript read straight by Metro and Vite, with no build step, and runs in plain Node: it never imports `react-native`, `expo-*`, the DOM, `app/` or `web/`. UI, platform calls and the adapters that feed core a platform (`src/api/client.ts`, `src/hooks/useBookingActions.ts`, `src/hooks/useAdminActions.ts`, `src/hooks/useFocusLoad.ts`) stay in the clients, which depend on core and never on each other.
- New date helpers, strings and other shared logic go in `core/`, tested there. What only the desktop calendar needs goes in `web/src/desktop/weeks.ts`.
- Some client files read the same in both but bind platform code, such as `config.tsx` and `src/auth/session.tsx`. `scripts/check-mirrors.mjs` lists them and fails when the copies differ, so change both.
- Every visible string lives in `core/src/i18n/sv.ts` and `core/src/i18n/en.ts`. A new string goes in both, and TypeScript refuses an English catalog that lacks a Swedish key. Components read it with `useMessages()`; helpers outside components take it as a `t: Messages` argument. Never write UI text inline.
- The organization picks its languages (`locales`), and the clients show only those. Its own text (resource and kind names, tags, rules, announcements) is jsonb with a value per language. The server resolves it from `Accept-Language`, so member endpoints return plain strings and admin endpoints the whole object (`server/src/lib/locale.ts`). Untranslated text falls back to a language it is written in.
- The language is per device: the one picked under Lägenhet / Apartment or Föreningen / Association, else the first device language the organization uses, else English if it uses it, else the organization's first language. Push tokens carry it, and the server writes push in it. The server also keeps it on the account from each request (`getSignedIn`), so mail sent outside a request is written in it too.
- `web/` is on Tailwind v4 (CSS-first, tokens in `@theme`); `app/` stays on the v3 LTS that NativeWind needs. Do not copy config between them.
- Match the app's result, not its layout mechanism. Anything sized from the viewport in React Native is wrong on web, where one breakpoint spans phone to laptop.
- Keep the clients symmetric. No hook or helper file in one client unless the other gets the same shape, except for what only the web has: keyboard navigation and mouse drag (`useRoving*`, `useDragScroll`, `lib/inputModality.ts`), the service worker and web push prompt, the address bar (`lib/route.ts`), and the desktop layout (`src/desktop/`, `lib/media.ts`, and `lib/slots.ts`, which it shares with the phone layout). The app alone has `usePageScroll` in `AdminPage`, for headings that stick, which the web does with CSS `sticky`. Short logic stays inline in the component.
- Data loading is hand-rolled, in `core/src/load/`; a screen loads through its client's `useFocusLoad`. Never add TanStack Query, SWR or another server-state library.
- Ask and tell through `useDialog`, never `Alert.alert` or `window.confirm`. Both clients draw every dialog themselves in `src/components/Dialog.tsx`, the app's with a queue and the screen-reader handling an alert would give for free, so the look and the button conventions live in one place.
- Layout that depends on the mobile viewport (`dvh`/`vh`, fixed bottom bars, safe areas) cannot be verified in desktop Chrome, nor by a script that fakes a width, since the toolbar never collapses there. Prefer designs without viewport units; otherwise report it as unverified and needing a real phone, and do not call it verified.
- If web push shows as Chrome instead of BrfHub on macOS, that is Chrome's `AppShimNotificationAttribution` feature flag, not our code. Do not touch `push-sw.js` or the manifest for it.

# Rules

- Reuse existing helpers and components. Search before writing a new one.
- Text people type into a request body goes through `textSchema` or `optionalTextSchema` in `server/src/lib/text.ts` (trimmed, bounded, no control characters; `multiline` keeps line breaks), and a push token through `pushTokenBodySchema` in `server/src/pushToken/pushToken.dto.ts`. Never `z.string()` with ad hoc bounds for either.
- In `app/` and `web/`, import with the `@/` alias (and an image under `app/assets/` with `@assets/`), never `../`, and core as `@brfhub/core/<path>`, such as `@brfhub/core/lib/dates`. `core/` and `server/` have no alias and use relative imports; `@/` in core would point into whichever client imports it.
- drizzle/ is .gitignored as of now during development, no need to bring it up.
- Declare a composite `unique` in the table's column order: drizzle-kit reads it back that way, and any other order makes every push offer to truncate the table.
